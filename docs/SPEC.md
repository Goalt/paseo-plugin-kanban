# ТЗ: плагин «Kanban board» для Paseo

Статус: **на ревью у заказчика**. Версия 1.0, 2026-09-06.

## 1. Цель

Родная kanban-доска внутри всех клиентов Paseo (браузер, desktop, mobile), отображающая и
управляющая теми же данными, которые агенты уже ведут через MCP-инструменты хаба
(`mcp__hub__kanban-*`). Пользователь видит доску прямо в Paseo — без отдельного веб-UI на
непроброшенном порту, — а изменения агентов появляются на ней сами, в реальном времени.

## 2. Исходная система (результат обследования)

| Что | Факт |
|---|---|
| Продукт | [gablabelle/mcp-kanban](https://github.com/gablabelle/mcp-kanban) v0.1.1, MIT |
| Где стоит | `~/mcp-hub/servers/mcp-kanban`, запускается внутри контейнера `mcp-hub` |
| MCP | stdio-сервер, 16 инструментов (create/update/move/delete ticket, subtasks, sessions, projects, columns, open/stop board), в хабе — префикс `kanban` |
| Web-сервер | Hono, порт **3010** внутри контейнера: REST `/api/*` + WebSocket `/ws` + собственный React-UI |
| Данные | SQLite `/root/.mcp-kanban/kanban.db` **внутри контейнера** (writable layer, не том) |
| Доступность из демона Paseo | `http://mcp-hub:3010/api/health` → `{"ok":true}` — контейнеры в общих docker-сетях, имя резолвится DNS'ом |
| Модель | projects → columns (Backlog / Todo / In Progress / Review / Done) → tickets: `ticket_number`, `title`, `description` (markdown), `priority` (urgent/high/medium/low), `column_id`, `session_id`, `parent_ticket_id` (сабтаски), `order`. Плюс sessions (имя+цвет+branch), dependencies (blocked_by/blocks/related_to), attachments |
| Live-события WS | `ticket:created/updated/moved/deleted`, `subtask:completed`, `session:created/deleted`, `column:updated` |

REST-эндпоинты тикетов: `GET/POST /api/tickets`, `GET/PUT/DELETE /api/tickets/:id`,
`PUT /api/tickets/:id/move`, `GET/POST /api/tickets/:id/subtasks`,
`GET /api/tickets/:id/attachments`, `GET/POST /api/tickets/:id/dependencies`;
аналогично `/api/projects`, `/api/columns`, `/api/sessions`.

## 3. Архитектура плагина

Trusted local plugin для Paseo **0.6.1** (текущий демон), по образцу уже работающих
`~/paseo-plugins/modal-ui` и `~/paseo-plugins/docker-containers`:

```
Paseo client (браузер/desktop/mobile)
   └─ board.client.tsx  ── useRpc ──►  index.ts (сервер плагина в демоне)
                                          ├─ REST http://mcp-hub:3010/api/*
                                          └─ WS ws://mcp-hub:3010/ws  (версия доски++)
```

- **Сервер плагина** (`index.ts`) — типизированный RPC-прокси (`defineRpc`/`plugin.handle`, zod):
  - `kanban.snapshot` — вся доска одним ответом: проект, колонки, тикеты с прогрессом сабтасков, сессии + `version`;
  - `kanban.version` — только номер версии (лёгкий поллинг);
  - `kanban.ticket` — детали тикета (сабтаски, зависимости, вложения);
  - мутации: `kanban.createTicket`, `updateTicket`, `moveTicket`, `deleteTicket`, `createSubtask`, `completeSubtask`;
  - `kanban.projects` — список проектов (переключатель).
- **Live-обновления**: сервер плагина держит WebSocket к kanban и на каждое событие
  инкрементирует `version`. Клиент раз в ~2 с опрашивает `kanban.version` и при изменении
  перезабирает снапшот. (RPC 0.6.1 — только запрос-ответ, push с сервера в клиент нет;
  поллинг версии — копейки, полный снапшот тянется только при реальном изменении.)
  При обрыве WS — реконнект с бэкоффом; поллинг при этом продолжает работать как fallback.
- **Адрес kanban** — константа `http://mcp-hub:3010` с возможностью переопределить через
  переменную окружения демона `KANBAN_URL`. IP не хардкодим (урок nginx: кэш IP → 502).
- **Если API недоступен** — понятный экран ошибки с кнопкой Retry; сервер плагина при этом
  пробует поднять борду сам: `docker exec mcp-hub node /app/servers/mcp-kanban/dist/cli/index.js start --no-open`
  (идемпотентно: у CLI есть проверка «уже запущено»).

## 4. UI/UX (v1)

Точки входа: пункт сайдбара **Kanban**, вкладка воркспейса/эксплорера, команда в
Command Center «Open Kanban board».

**Доска**: переключатель проектов сверху; колонки горизонтальной лентой (ScrollView),
внутри — вертикальный скролл карточек. Карточка: `#номер`, заголовок, цветной бейдж
приоритета, цветная метка сессии агента, прогресс сабтасков `n/m`. Пустые колонки и пустая
доска — с явными empty-state.

**Детали тикета** (модалка по тапу): описание, приоритет, сессия, список сабтасков с
чекбоксами (завершение), зависимости, выбор колонки, удаление (с подтверждением).

**Создание**: кнопка «+» в шапке колонки → модалка: title (обязателен), description, priority.

**Перемещение**: выбор колонки в модалке + кнопки «◀ ▶» на карточке (в соседнюю колонку).
Настоящего drag&drop в v1 **нет** — в клиентском рантайме плагинов его нечем сделать
(кросс-платформенный DnD — открытая issue апстрима #3558 даже для будущей v0.8).

**Тема**: только цвета из `theme` плагина — светлая/тёмная автоматически.

## 5. Жёсткие ограничения совместимости (проверены на этом демоне)

1. Точка входа `index.ts` + отдельные `*.client.tsx` (формат 0.6.1, не `index.client.tsx` из v0.8).
2. В клиентском коде **ни одного `async`/`await`** — компилятор 0.6.1 не понижает синтаксис,
   Hermes на iOS/Android молча не грузит плагин. Только промис-цепочки.
3. Импорты клиента: только `react`, `react-native`, `@getpaseo/plugin`. Никаких `@dnd-kit`,
   `react-markdown` и прочих npm-зависимостей в клиентском бандле. Описание тикета в v1 —
   плоский текст (упрощённый markdown: заголовки/списки жирностью — по возможности, без библиотек).
4. Ошибки сети не должны ронять плагин: каждый RPC возвращает `{ok, error, ...}`.

## 6. Вне рамок v1

Drag&drop; полноценный markdown-рендер; просмотр содержимого attachments (покажем только
имена файлов); редактирование/создание колонок; создание и удаление проектов из UI
(делается агентом через MCP); управление сессиями; настройки борды; правка `order` внутри
колонки (тикеты сортируются как отдаёт API).

## 7. Риски

- **База в writable layer mcp-hub** — пропадёт при пересоздании контейнера. Это свойство
  текущей установки, не плагина; рекомендация вне рамок ТЗ: перенести `~/.mcp-kanban` на том
  `/data` (симлинк) — могу сделать отдельной задачей.
- Борда на 3010 стартует только по `open_board`/нашему авто-старту; после рестарта mcp-hub
  плагин поднимет её сам (см. §3).
- На iPhone плагин появится только в приложении Paseo ≥0.5 (в App Store — 0.7.2); клиент
  0.4.0 плагины не умеет. Демо-видео пишутся с браузерного клиента демона.

## 8. Спринты

Разработку и тестирование каждого спринта ведут **субагенты Paseo** (`create_agent` /
`send_agent_prompt`), приёмку — я. Ход работ ведём на самой kanban-доске (dogfooding:
тикеты спринтов агенты двигают через `mcp__hub__kanban-*` — это же и живой тест-стенд).
Заказчику по завершении каждого спринта — **только демо-видео** (CDP-screencast живого
Paseo UI с подсветкой кликов, как в скилле expo-demo-capture).

План заведён на kanban-доску, проект **kanban-board**: 6 историй (по две на спринт),
30 сабтасков. Номера ниже — `ticket_number` на доске.

**Спринт 1 — каркас и чтение (read-only MVP).** Выход: живая доска в Paseo, обновляющаяся
сама, когда агент меняет тикеты через MCP. Видео №1.

- **#1 Сервер плагина: RPC-прокси к kanban API** (high):
  #7 каркас проекта и установка в демон · #8 RPC-контракт в contract.ts ·
  #9 HTTP-слой к kanban REST (KANBAN_URL, сборка снапшота) ·
  #10 WS-версионирование (подписка /ws, version++, реконнект с бэкоффом) ·
  #11 авто-старт борды при недоступном API (docker exec, идемпотентно)
- **#2 UI доски read-only + live-обновление** (high):
  #12 вёрстка колонок и карточек · #13 переключатель проектов ·
  #14 live-поллинг версии (~2 с, защита от гонок) · #15 empty-states и экран ошибки с Retry ·
  #16 тестирование спринта на живом UI (CDP-чек-лист) · #17 демо-видео №1

**Спринт 2 — управление тикетами.** Выход: полный CRUD с доски, каждое действие сверено
с данными через MCP и родной web-UI. Видео №2.

- **#3 Модалка деталей и перемещение** (medium):
  #18 RPC kanban.ticket + moveTicket · #19 модалка деталей ·
  #20 перемещение: выбор колонки + кнопки ◀▶ · #21 обработка ошибок мутаций, защита от дублей
- **#4 CRUD тикетов и сабтаски** (medium):
  #22 RPC мутаций CRUD/сабтасков · #23 создание тикета из колонки («+») ·
  #24 редактирование в модалке · #25 сабтаски: чекбоксы и создание ·
  #26 удаление с подтверждением · #27 тестирование: сверка данных с двух сторон ·
  #28 демо-видео №2

**Спринт 3 — полировка и релиз.** Выход: сданный проект — репозиторий, README,
приёмка по §10. Видео №3.

- **#5 Полировка: сессии, зависимости, темы** (low):
  #29 цветные метки сессий + фильтр · #30 зависимости в модалке ·
  #31 счётчик In Progress (если SDK позволяет бейдж — у сайдбара, иначе в шапке) ·
  #32 полировка тем и пустых состояний
- **#6 Релиз** (medium):
  #33 README + CHANGELOG · #34 публикация приватного репо (блокер: PAT) ·
  #35 приёмка по критериям §10 · #36 демо-видео №3

Порядок исполнения: #1 → #2 (внутри спринта 1 сервер раньше UI), #3 → #4, #5 → #6.
Зависимость между спринтами строгая: спринт N+1 не стартует до сдачи видео спринта N.

## 9. Репозиторий

Приватный репозиторий `paseo-plugin-kanban` на GitHub: исходники плагина, README
(установка, ограничения 0.6.1, архитектура), CHANGELOG по спринтам. Коммит в конце каждого
спринта. Видео в репозиторий не кладём (размер) — отдаются в чат.

**Блокер**: на машине нет GitHub-авторизации (`gh` не залогинен, PAT в сохранённых ключах
не найден). Нужен от заказчика PAT со scope `repo` (или `gh auth login` в интерактиве).
До появления токена репозиторий ведётся локально в git, публикация — последним шагом.

## 10. Критерии приёмки проекта

1. Плагин `kanban-board` в статусе `running`, клиентский бандл без `async` (проверка grep + смоук на клиенте).
2. Доска показывает актуальное состояние `kanban.db`; изменения через MCP-инструменты видны ≤3 с без действий пользователя.
3. CRUD с доски отражается в данных (проверка через `list_tickets`/`get_ticket`).
4. Недоступный kanban API → внятная ошибка и восстановление после Retry, не крэш.
5. Три демо-видео сданы; репозиторий опубликован приватным (после получения токена).

## Решения по умолчанию (можно ветировать на ревью)

1. Имя плагина/репо: `kanban-board` / `paseo-plugin-kanban`.
2. Перемещение тикетов кнопками, без DnD (техпричины — §4-§5).
3. Описание тикета — плоский текст, не markdown.
4. Проекты из плагина не создаются/не удаляются — только переключение.
5. Видео — с браузерного клиента Paseo (мобильный клиент к демо-стенду не подключён).
